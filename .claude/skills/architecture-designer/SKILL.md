# 아키텍처 설계 스킬

이 스킬은 소프트웨어 아키텍처 설계 산출물을 작성하거나 검토할 때, 아래 모든 기준을 동시에 만족하도록 안내한다. 어느 하나라도 빠지면 산출물을 완료된 것으로 보고하지 않는다.

## 1. 표준 준수 범위

- **A-SPICE SWE.2 (Software Architectural Design)**: 아키텍처 산출물이 다음을 충족하는지 자체 점검한다 — 요구사항이 아키텍처 요소에 할당됨, 아키텍처 요소 간 인터페이스가 정의됨, 아키텍처 요소의 동적 동작이 기술됨, 자원 사용 목표(메모리/CPU/타이밍 등, 해당 시)가 정의됨, 대안 아키텍처를 평가한 근거가 있음, 요구사항↔아키텍처 양방향 추적성이 확보됨, 일관성이 유지됨. 정확한 기본관행(BP) 문구는 조직이 보유한 공식 A-SPICE 4.1 PAM으로 대조 확인이 필요하다.
- **ISO 26262 Part 6, Clause 7 (Software architectural design)**: 아키텍처는 컴포넌트, 내/외부 인터페이스, 동적 동작, (해당 시) 자원 사용을 명시해야 한다. 계층적 분해 시 설계 원칙(정보 은닉, 인터페이스 크기 제한, 응집도 확보, 결합도 최소화, 적절한 세분화 수준, 유지보수성, 명확한 구문·의미의 인터페이스 정의)을 따른다. 안전 관련 요구사항이 있는 요소는 ASIL 등급을 상속·표시하고, 서로 다른 ASIL이 공존하는 경우 간섭으로부터의 자유(freedom from interference, ISO 26262-9)를 검토한다. 표기법(비정형/반정형 UML·SysML/정형)과 검증 방법(워크스루, 인스펙션, 시뮬레이션, 프로토타입, 정형검증, 제어/데이터 흐름 분석 등)은 ASIL 등급에 맞게 선택한다. 정확한 표·조항 번호는 조직이 보유한 공식 ISO 26262:2018 Part 6 문서로 대조 확인이 필요하다.

## 2. 대안 아키텍처 제안 및 사용자 선정 (필수, 상세 설계보다 먼저)

- 요구사항(가능하면 `traceability-matrix` 또는 REQ-F/REQ-NF 목록)을 검토한 뒤, 상세 설계에 들어가기 **전에** 최소 2~3개의 후보 아키텍처 스타일을 제안한다. 요구사항 특성에 맞는 후보를 고른다 (예: 계층형(Layered), 포트-앤-어댑터/헥사고날, 마이크로커널·플러그인, 이벤트 기반/Pub-Sub, 파이프-필터, 서비스 지향 등). 후보를 지어내지 말고 실제로 해당 요구사항에 적용 가능한 스타일만 제시한다.
- 각 후보마다 다음을 표로 비교 제시한다: 구조 개요(간단한 다이어그램 또는 텍스트 설명), 응집도/결합도에 미치는 영향, 변경 유연성(예상되는 변경 지점을 얼마나 잘 격리하는지), SOLID 원칙 부합도, 통합 순서에 미치는 영향, 안전(ASIL 분리/간섭으로부터의 자유) 영향, 주요 리스크/트레이드오프.
- **사용자가 후보 중 하나를 선택하기 전까지 §3~§8의 상세 설계(인터페이스 정의, 통합 순서, 최종 다이어그램 등)를 확정하지 않는다.** 선택을 기다리는 동안에는 비교표까지만 제시하고 사용자에게 선택을 요청한다.
- 사용자가 후보를 혼합하거나 수정해서 채택하는 것도 허용하되, 최종 채택안과 그 근거를 산출물에 기록한다.

## 3. 응집력·결합도·변경 유연성 (필수, 완화 불가)

- **높은 응집력**: 각 컴포넌트는 단일하고 명확한 책임(하나의 기능적 관심사)만 담당해야 한다. 서로 관련 없는 기능이 한 컴포넌트에 섞여 있으면 분리한다.
- **낮은 결합도**: 컴포넌트는 §5에서 정의한 인터페이스를 통해서만 상호작용한다. 다음을 결합도 위반으로 간주하고 발견 시 재설계한다: 다른 컴포넌트의 내부 상태/필드에 직접 접근, 전역 변수·공유 가변 상태를 통한 암묵적 통신, 구체 구현 클래스에 대한 직접 참조(추상화 없이), 순환 의존(A→B→A).
- **변경 유연성**: 요구사항 변경이 예상되는 지점(변동점, variation point)을 식별하고, 이를 인터페이스/추상화 뒤로 캡슐화해 변경의 영향 범위를 해당 컴포넌트 내부로 국한시킨다. 설정 가능한 값은 하드코딩하지 않고 외부화한다.
- 아키텍처 산출물에는 응집도/결합도/변경 유연성 관점의 자체 평가 결과(컴포넌트별 책임 요약, 식별된 결합 지점과 완화 방법)를 반드시 포함한다.

## 4. SOLID 원칙 (필수)

컴포넌트/인터페이스 설계 시 아래를 모두 점검하고, 위반이 있으면 재설계하거나 위반을 감수하는 근거를 명시적으로 기록한다.

- **SRP (단일 책임)**: 컴포넌트는 변경되어야 할 이유가 하나뿐이어야 한다.
- **OCP (개방-폐쇄)**: 새로운 동작 추가는 기존 컴포넌트 수정이 아니라 인터페이스 구현 추가/확장으로 가능해야 한다. §2에서 식별한 변동점을 이 원칙으로 캡슐화한다.
- **LSP (리스코프 치환)**: 동일 인터페이스의 대체 구현체는 호출자가 기대하는 계약(사전조건을 강화하지 않고, 사후조건을 약화하지 않음)을 위반하지 않아야 한다.
- **ISP (인터페이스 분리)**: 클라이언트가 사용하지 않는 오퍼레이션까지 포함한 "뚱뚱한" 인터페이스를 금지한다. 사용자(클라이언트)별로 필요한 오퍼레이션만 묶어 인터페이스를 분리한다.
- **DIP (의존성 역전)**: 상위(정책) 컴포넌트는 하위(구현) 컴포넌트의 구체 클래스가 아니라 추상 인터페이스에 의존한다. 의존성 방향이 안정적인 추상화를 향하는지 확인한다.

## 5. 컴포넌트 인터페이스 정의 (필수, 완화 불가)

- **컴포넌트 간의 모든 통신은 정의된 인터페이스를 통해서만 이루어진다.** 인터페이스가 없는 직접 호출·직접 데이터 접근은 허용하지 않는다.
- 각 인터페이스마다 다음 항목을 모두 명시해야 "정의됨"으로 인정한다:
  - 인터페이스 ID/이름, 제공(provider) 컴포넌트, 사용(consumer) 컴포넌트
  - 오퍼레이션 시그니처: 이름, 입력/출력 파라미터(타입, 단위, 유효 범위), 반환값
  - 사전조건(precondition) / 사후조건(postcondition)
  - 오류·예외 처리 방식(오류 코드, 예외, 타임아웃 등)
  - 동기/비동기 여부 및 타이밍 제약(해당 시 — 실시간 요구가 있는 경우 응답시간/주기 명시)
  - 데이터 무결성·스레드 안전성 요구사항(해당 시)
- provided/required 인터페이스는 UML/SysML Component Diagram으로 표현하고(§7), 동적 흐름은 Sequence/Activity Diagram으로 인터페이스 오퍼레이션 호출 순서를 보인다.
- 인터페이스 시그니처와 시퀀스 다이어그램상의 호출이 서로 일치하는지 상호 검증한다.

## 6. 컴포넌트 통합 순서 정의 (필수)

- 확정된 아키텍처의 컴포넌트 의존성 그래프를 도출하고, 이를 바탕으로 통합 순서(하위/공통 컴포넌트 → 상위/의존 컴포넌트)를 위상 정렬(topological order) 기준으로 정의한다.
- 순환 의존이 있으면 통합 순서를 정할 수 없으므로, 먼저 §3의 결합도 위반으로 처리하여 아키텍처를 수정한다.
- 각 통합 단계(스테이지)마다 다음을 명시한다: 해당 단계에서 통합되는 컴포넌트, 아직 통합되지 않은 하위 컴포넌트를 대신할 스텁/목(mock) 필요 여부, 단계별 통합 확인에 필요한 최소 시험 항목.
- 이 통합 순서는 이후 SWE.5(소프트웨어 통합 및 통합시험)의 통합전략 산출물(`TPL-SWE5-001`)의 입력이 됨을 산출물에 명시하고, 두 문서 간 불일치가 없는지 확인한다.

## 7. 다이어그램

- `TPL-SWE2-002` drawio 템플릿을 사용하거나, 초안/검토 단계에서는 Mermaid/PlantUML 코드 블록(텍스트 기반, 렌더링 가능)을 사용한다.
- 최소한 다음 다이어그램을 포함한다:
  - **Component Diagram**: 컴포넌트와 provided/required 인터페이스, 컴포넌트 간 의존 방향
  - **동적 동작 다이어그램**: 주요 시나리오별 Sequence Diagram 또는 Activity/State Machine Diagram
  - **통합 순서 다이어그램**: §6의 통합 단계를 시각화(단계별 컴포넌트 그룹)
  - 필요 시 SysML Requirement Diagram으로 요구사항↔아키텍처 요소의 `satisfy`/`allocate` 관계 표기
- 각 다이어그램에는 관련 요구사항 ID·인터페이스 ID를 라벨/주석으로 명시해 추적이 끊기지 않게 한다.

## 8. 안전(ASIL) 및 추적성

- 안전 관련 요구사항을 만족하는 컴포넌트는 해당 ASIL 등급과 연계된 안전목표(Safety Goal)/안전요구사항을 명시한다.
- 서로 다른 ASIL이 하나의 아키텍처 요소에 공존하면, 간섭으로부터의 자유(freedom from interference) 검토 필요 여부를 명시하고, 필요 시 공간적/시간적 분리(예: 별도 프로세스/파티션, 메모리 보호, 타이밍 격리) 메커니즘을 아키텍처에 반영한다. 근거 없이 ASIL 분해/공존을 그냥 넘어가지 않는다.
- 모든 요구사항(REQ-F/REQ-NF)은 하나 이상의 아키텍처 컴포넌트에 할당되어야 하며, `TPL-TRC-001` 매트릭스에 반영한다. 요구사항이 어느 컴포넌트에도 할당되지 않았거나, 컴포넌트가 어떤 요구사항도 만족하지 않는 "고아(orphan)" 상태는 완료로 보지 않고 사용자에게 보고한다.

## 9. 일관성 및 검증

- 표기법(다이어그램 종류·기호)을 산출물 전체에서 통일한다.
- 순환 의존, 인터페이스 시그니처 불일치, 요구사항 미할당 등을 점검하고 발견된 문제를 빠짐없이 보고한다.
- ISO 26262-6에서 언급하는 검증 방법(워크스루/인스펙션/시뮬레이션/프로토타입/정형검증/제어·데이터 흐름 분석) 중 어떤 방법으로 이 아키텍처를 검토했는지 기록한다.
