# 소프트웨어 통합시험 스킬

이 스킬은 소프트웨어 통합 및 통합시험 산출물을 작성하거나 수행할 때, 아래 모든 기준을 동시에 만족하도록 안내한다. 어느 하나라도 빠지면 산출물을 완료된 것으로 보고하지 않는다.

**역할 범위**: 이 스킬은 A-SPICE SWE.5(아키텍처 인터페이스·통합 순서 기반 화이트박스 통합시험, 구조적 커버리지)만 다룬다. 요구사항 명세서를 테스트 베이시스로 하는 SWE.6 수준의 블랙박스 시스템 테스트 케이스 설계는 `sw-system-test` 스킬(sw-system-tester 서브에이전트)의 소관이며, 이 스킬에서 대신 수행하거나 내용을 중복 정의하지 않는다. 단위 수준 TDD 테스트는 `tdd` 스킬(coding 서브에이전트)의 소관이다.

## 0. 템플릿 확인 (최우선, 매번 반복)

- 통합시험 관련 산출물은 저장소의 지정 템플릿을 **반드시** 사용한다. 스스로 구조를 지어내지 않는다.
  - SW 통합전략 및 통합시험 명세서 → `templates/WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-001_SW 통합전략 및 통합시험 명세서 템플릿.docx`
  - SW 통합시험 케이스 → `templates/WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-002_SW 통합시험 케이스 템플릿.xlsx`
  - SW 통합시험 결과서 → `templates/WP_Templates/Engineering/SoftwareComponentVerificationAndIntegrationVerification/TPL-SWE5-003_SW 통합시험 결과서 템플릿.xlsx`

## 1. 표준 준수 범위

- **A-SPICE SWE.5 (Software Integration and Integration Test)**: 산출물이 다음을 충족하는지 자체 점검한다 — 아키텍처에 근거한 통합전략(통합 순서 포함)이 수립됨, 통합시험이 그 전략에 따라 명세됨, 시험 커버리지가 통합시험 스위트에 의해 검증됨(§5), 유닛의 통합상태가 확인됨(단위시험 통과 여부), 통합시험이 실제로 수행됨, 요구사항↔아키텍처↔통합시험 양방향 추적성이 확보됨, 일관성이 유지됨, 결과가 요약·공유됨. 정확한 기본관행(BP) 문구는 조직이 보유한 공식 A-SPICE 4.1 PAM으로 대조 확인이 필요하다.
- **ISO 26262 Part 6, Clause 10 (Software integration and testing)**: 통합시험 케이스는 아키텍처 설계(인터페이스, 동적 동작)를 테스트 베이시스로 도출해야 한다. ASIL 등급에 맞는 시험기법(§4 — 요구사항 기반 시험, 인터페이스 시험, 결함주입 시험, 자원사용 시험, 백투백 비교 시험 등)을 선택하고, 구조적 커버리지 지표(함수 커버리지, Call 커버리지 — §5)를 측정한다. 정확한 표·조항 번호는 조직이 보유한 공식 ISO 26262:2018 Part 6 문서로 대조 확인이 필요하다.
- **프로젝트 정책**: 표준상의 ASIL별 권고 수준과 무관하게, 이 프로젝트는 함수 커버리지·Call 커버리지 **100%**를 모든 통합시험의 필수 목표로 한다(§5).

## 2. 테스트 베이시스 확보 — 아키텍처 근거 (필수, 선행)

- 확정된 아키텍처 설계서(`TPL-SWE2-001`)의 인터페이스 정의(§5)와 통합 순서(§6)를 테스트 베이시스로 사용한다. 아키텍처 산출물이 없거나 불명확하면 통합시험을 시작하지 말고, architecture-designer 산출물을 먼저 확보하거나 사용자에게 확인한다.
- 인터페이스나 통합 순서를 스스로 새로 만들거나 아키텍처와 다르게 재해석하지 않는다. 아키텍처의 인터페이스 시그니처(사전/사후조건, 오류 처리, 타이밍 제약)를 시험 기대값의 근거로 그대로 사용한다.
- 통합 대상 유닛이 이미 단위시험(SWE.4, `TPL-SWE4-002`)을 통과했는지 확인한다. 단위시험이 완료되지 않은 유닛은 통합 대상에서 제외하거나 스텁으로 대체하고, 그 사실을 명시한다.

## 3. 통합 순서 준수 — 단계적 통합 (필수, 완화 불가)

- 아키텍처 §6에서 정의한 통합 순서(의존성 위상 정렬)를 그대로 따른다. 임의로 순서를 바꾸거나 상위(의존하는) 컴포넌트를 먼저 통합하지 않는다.
- 각 통합 단계마다 다음을 명시한다: 이번 단계에서 새로 통합되는 컴포넌트, 아직 통합되지 않은 하위 컴포넌트를 대신할 스텁/드라이버 필요 여부, 이 단계의 완료 판정 기준(해당 단계 시험 케이스 전부 pass + §5 커버리지 기준 충족).
- 실제 시험 순서가 아키텍처의 통합 순서와 다르면 불일치로 보고하고, 사용자 승인 없이 순서를 임의 변경하지 않는다.

## 4. 시험기법 (ISO 26262-6 기반, 필수)

각 인터페이스/통합 단계마다 아래 기법 중 해당하는 것을 적용하고, 어떤 기법을 왜 선택했는지 시험 명세에 기록한다:

- **요구사항 기반 시험(Requirements-based test)**: 아키텍처 컴포넌트에 할당된 요구사항이 통합된 컴포넌트 조합에서 만족되는지 검증한다.
- **인터페이스 시험(Interface test)**: 아키텍처 §5의 인터페이스 명세(오퍼레이션 시그니처, 사전/사후조건, 오류 처리, 타이밍 제약)를 실제 호출로 검증한다. 인터페이스를 거치지 않는 통신(직접 내부 접근, 전역 상태 공유 등)이 없는지도 함께 확인한다.
- **결함주입 시험(Fault injection test)**: 인터페이스의 오류 처리 경로(잘못된 입력, 타임아웃, 예외적 상황)가 설계대로 동작하는지 검증한다.
- **자원사용 시험(Resource usage test)**: 아키텍처에 자원 사용 목표(실행시간, 메모리 등)가 정의되어 있으면, 통합 후에도 그 목표가 지켜지는지 검증한다.
- **백투백 비교 시험(Back-to-back test)**: 모델 기반 개발을 사용하는 프로젝트에서만 적용 — 모델 시뮬레이션 결과와 통합된 코드의 실행 결과를 비교한다. 모델 기반 개발을 사용하지 않으면 해당 없음을 명시하고 생략한다.
- 위 기법의 정확한 표·조항 번호는 조직이 보유한 공식 ISO 26262:2018 Part 6 문서로 대조 확인이 필요하다.

## 5. 구조적 커버리지·테스트 성공률 — 100% (필수, 완화 불가)

- **함수 커버리지(Function Coverage)**: 통합된 코드 내 모든 함수가 통합시험 중 최소 1회 이상 실행되었는지 측정한다.
- **Call 커버리지(Call Coverage)**: 아키텍처/상세설계에서 정의된 모든 호출 관계(인터페이스 오퍼레이션 호출 지점, 함수 간 호출)가 통합시험 중 최소 1회 이상 실행되었는지 측정한다.
- 두 지표 모두 **100%**를 목표로 하며, 오픈소스 커버리지 측정 도구(예: `coverage.py`의 함수 단위 리포트, 호출 그래프 분석 도구)로 실측한다. 실행 결과(수치, 사용 도구, 재현 가능한 실행 명령)를 산출물에 기록한다. 추정치나 "충분히 커버했다"는 서술로 100%를 대체하지 않는다.
- 100%에 미달한 함수/호출 경로가 있으면, 해당 부분을 커버하는 시험 케이스를 추가해 §3의 해당 통합 단계를 완료 처리하지 않는다.
- **테스트 성공률 100%**: 실행된 통합시험 케이스는 fail 없이 모두 pass해야 한다(§3·§7의 단계 완료 판정과 동일한 기준). fail이 있으면 결함으로 기록하고 수정 후 재시험하며, 완료로 보고하지 않는다.
- 물리적으로 도달 불가능한 코드(예: 방어적 코드, 이론상 발생 불가능한 분기)가 있어 100% 달성이 불가능한 경우에만 예외로 다룬다 — 그 코드와 도달 불가능한 근거를 구체적으로 명시하고, 스스로 기준을 낮추지 말고 사용자에게 예외 승인을 요청한다.

## 6. 시험 케이스 설계 및 명세

- `TPL-SWE5-002`(통합시험 케이스 템플릿)에 각 시험 케이스를 기록한다: 케이스 ID, 대상 인터페이스/컴포넌트 조합, 적용 기법(§4), 사전조건, 입력, 기대결과(아키텍처 인터페이스의 사후조건 기반), 실제결과, 판정(pass/fail), 관련 요구사항 ID·아키텍처 인터페이스 ID.
- 각 시험 케이스는 긍정(Positive, 정상 흐름)/부정(Negative, 오류·예외 흐름) 여부를 명시한다.
- 각 통합 단계(§3)에서 새로 커버되는 인터페이스를 해당 단계의 시험 케이스와 명시적으로 연결한다.

## 7. 시험 수행 및 결과

- `TPL-SWE5-003`(통합시험 결과서)에 실행 결과, §5의 커버리지 측정 결과, 발견된 결함, 이전 단계 대비 회귀 여부를 기록한다.
- 통합 단계 완료 판정: 해당 단계의 모든 시험 케이스가 pass하고, 그 단계까지 통합된 코드 범위에서 함수·Call 커버리지가 100%(또는 §5의 예외 승인을 받은 부분 제외)여야 다음 단계로 진행한다.

## 8. 추적성 및 일관성

- `TPL-TRC-001`을 갱신해 요구사항 → 아키텍처 컴포넌트/인터페이스 → 통합시험 케이스의 양방향 추적을 유지한다.
- 아키텍처에 정의된 인터페이스 중 대응하는 시험 케이스가 없는 것("미검증 인터페이스")과, 시험 케이스인데 대응하는 요구사항·인터페이스가 없는 것("고아 케이스")을 점검하고 발견 시 보고한다.
- 아키텍처 설계서의 인터페이스·통합 순서와 실제 통합시험 명세·수행 순서 간 불일치가 없는지 점검한다.

## 9. 출력 형식

실제 산출물은 `TPL-SWE5-001`(전략/명세), `TPL-SWE5-002`(케이스), `TPL-SWE5-003`(결과)의 장/절·시트 구조를 그대로 채워 작성한다. 템플릿이 다루지 않는 보조 내용이나 초안 검토 단계에서만 아래 골격을 임시로 사용한다.

```
# 소프트웨어 통합시험 요약: <대상 범위>

## 테스트 베이시스
- 아키텍처 설계서 버전/위치: ...
- 참조한 인터페이스 ID 목록: ...
- 참조한 통합 순서(§6) 단계 목록: ...

## 통합 단계별 진행
| 단계 | 통합 컴포넌트 | 필요 스텁/드라이버 | 적용 시험기법 | 시험 케이스 ID | 결과(pass/fail) |
|---|---|---|---|---|---|

## 구조적 커버리지 측정 결과
| 단계 | 함수 커버리지 | Call 커버리지 | 측정 도구 | 100% 미달 시 원인/조치 |
|---|---|---|---|---|

## 추적성 및 일관성 점검 결과
- TPL-TRC-001 갱신 여부: ...
- 미검증 인터페이스 / 고아 케이스 여부: ...
- 통합 순서 불일치 여부: ...
```
