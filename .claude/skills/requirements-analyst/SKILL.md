# 요구사항 분석가 스킬

이 스킬은 요구사항 산출물을 작성하거나 검토할 때, 아래 모든 기준을 동시에 만족하도록 안내한다. 어느 하나라도 빠지면 산출물을 완료된 것으로 보고하지 않는다.

## 0. 템플릿 확인 (최우선, 매번 반복)

- 요구사항 산출물이 따라야 할 템플릿이 저장소에 있는지 먼저 확인한다 (예: `templates/` 디렉터리, 사용자가 채팅에 첨부한 문서 등).
- **템플릿을 찾지 못했다면 스스로 템플릿을 지어내 확정하지 않는다.** 대신 아래 "0-1. 템플릿 부재 시 기본 구조"를 임시로 사용하고, 산출물 최상단에 다음 경고를 반드시 넣는다:

  > ⚠️ 템플릿 미제공 상태의 임시 구조입니다. 사용자가 지정한 템플릿이 도착하면 이 문서 전체를 그 템플릿 형식으로 재정렬해야 합니다.

- 템플릿이 나중에 제공되면, 기존에 작성된 모든 요구사항 항목을 새 템플릿 구조로 마이그레이션하고, 필드 누락이 없는지 재검증한다.

### 0-1. 템플릿 부재 시 기본 구조 (요구사항 1건당)

| 필드 | 내용 |
|---|---|
| ID | 고유 식별자 (§5 ID 규칙 참조) |
| 유형 | 기능(FR) / 비기능(NFR) |
| 제목 | 한 줄 요약 |
| 서술 | §2 EARS 구문을 따른 본문 |
| 출처 | 상위 요구사항/이해관계자 요구 ID |
| 우선순위 | 필수/권장/선택 등 |
| ASIL 등급 | 안전 관련 시 QM/A/B/C/D + 연계된 안전목표(Safety Goal) |
| 근거(Rationale) | 왜 필요한지 |
| 검증 방안 | §4 참조 (비기능), 기능은 다이어그램/시나리오 기반 검증 절차 |
| 추적 링크 | §5 참조 |
| 상태 | 초안 / 검토중 / 승인 |

## 1. 표준 준수 범위

- **ISO 26262**: 안전 관련 요구사항은 ASIL 등급과 안전목표(Safety Goal)를 명시적으로 연결한다. 요구사항 속성(검증 기준, 근거, 추적성)이 항상 함께 기록되어야 한다.
- **A-SPICE**: 요구사항 산출물이 SYS.1/SYS.2, SWE.1 프로세스가 요구하는 산출물 특성 — 완전성, 일관성, 검증 가능성, 추적 가능성 — 을 충족하는지 자체 점검한다. 정확한 기본관행(BP) 문구는 조직이 보유한 공식 A-SPICE 4.1 PAM으로 대조 확인이 필요하다.

## 2. 명확성(Clarity) 확보 규칙

- **EARS 구문**을 기본으로 사용한다 (필요 시 템플릿 서술 형식으로 대체):
  - 유비쿼터스: "`<시스템>`은 `<능력>`해야 한다."
  - 이벤트 기반: "`<트리거>`할 때, `<시스템>`은 `<반응>`해야 한다."
  - 상태 기반: "`<상태>`인 동안, `<시스템>`은 `<반응>`해야 한다."
  - 선택 기능: "`<기능>`이 있는 경우, `<시스템>`은 `<반응>`해야 한다."
  - 원치 않는 동작: "`<원치 않는 조건>`이 발생하면, `<시스템>`은 `<반응>`해야 한다."
- 한 문장 = 요구사항 하나(원자성). "그리고", "또한"으로 여러 요구를 한 문장에 묶지 않는다.
- 금지어(모호한 표현): "적절히", "충분히", "가능한 한", "일반적으로", "등등", "빠르게"(수치 없이) — 발견 시 구체적 수치/조건으로 재작성한다.
- 능동태를 사용하고 주어(시스템 또는 행위자)를 명시한다.
- 용어집(Glossary)을 유지하고, 동일 개념에는 항상 동일한 용어만 사용한다.

## 3. 기능요구사항 — UML/SysML 다이어그램

- 기능요구사항 그룹(유스케이스/기능 단위)마다 최소 1개의 다이어그램을 함께 제공한다.
- 다이어그램은 Mermaid 또는 PlantUML 코드 블록(텍스트 기반, 렌더링 가능)으로 표현한다.
- 요구사항 성격에 맞는 다이어그램 유형을 선택한다:
  - 행위자-시스템 상호작용 → Use Case Diagram
  - 처리 흐름/시나리오 → Sequence Diagram 또는 Activity Diagram
  - 상태 기반 동작 → State Machine Diagram
  - 요구사항 간 관계(포함/파생/만족) → SysML Requirement Diagram (`satisfy`/`derive`/`refine` 관계 표기)
- 각 다이어그램에는 관련 요구사항 ID를 라벨이나 주석으로 명시해 요구사항-다이어그램 간 연결을 끊기지 않게 한다.

## 4. 비기능요구사항 — ISO 25010 분류 + 실행 가능한 검증

- 각 비기능요구사항을 ISO/IEC 25010 품질특성(기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성) 중 하나 이상으로 태깅한다.
- 검증 방안은 다음을 모두 갖추어야 "실행 가능"으로 인정한다:
  - 측정 가능한 기준(정량 지표 + 임계값)
  - 구체적 검증 방법(사용 도구, 절차, 실행 환경)
  - 판정 기준(pass/fail 조건)
- **다음과 같은 표현은 검증 방안으로 인정하지 않는다**: "추후 결정", "적절한 수준에서 검증", "충분히 테스트", 도구/절차/기준 중 하나라도 빠진 서술. 이런 경우 완료 처리하지 말고, 실행 가능한 방안으로 다시 정의하거나 사용자에게 필요한 정보(도구/환경/임계값)를 확인한다.

## 5. 양방향 추적성(Traceability)

- 방안: 저장소 루트에 `traceability-matrix.md`를 유지한다. 열 구성: `상위 요구/이해관계자 요구 ID | 요구사항 ID | 유형 | 하위 산출물(설계/코드/테스트) ID | 상태`.
- 요구사항을 신규 작성하거나 수정할 때마다 이 매트릭스를 함께 갱신한다. 매트릭스 갱신 없이 요구사항만 추가하는 것은 완료로 보지 않는다.
- 하위 산출물이 아직 존재하지 않으면 `TBD`로 표시하고, 이후 설계/코드/테스트 산출물이 생기면 반드시 채워 넣는다.
- **ID 규칙**: 이해관계자 요구 `STK-NNN`, 기능요구사항 `REQ-F-NNN`, 비기능요구사항 `REQ-NF-NNN` (NNN은 3자리 일련번호). 번호는 재사용하지 않는다(삭제된 요구사항의 번호도 결번으로 남긴다).

## 6. 일관성(Consistency)

- 용어집에 없는 표현이나 용어집과 어긋나는 동의어 사용을 금지한다.
- 신규/수정 요구사항을 기존 요구사항 전체와 대조하여 모순(예: 동일 대상에 대해 상반된 값·조건 요구)이 없는지 점검하고, 발견 시 사용자에게 보고한다.
- ID 중복을 금지하고, 명명 규칙(§5)을 항상 동일하게 적용한다.

## 출력 형식

```
# <산출물명>

⚠️ (템플릿 미제공 시에만) 템플릿 미제공 상태의 임시 구조입니다 ...

## 용어집
| 용어 | 정의 |
|---|---|

## 기능요구사항
### <REQ-F-NNN> <제목>
- 서술: ...
- 출처: ...
- 우선순위 / ASIL 등급(해당 시): ...
- 근거: ...
- 다이어그램:
  ```mermaid
  ...
  ```
- 추적 링크: 상위 <STK-NNN> / 하위 <TBD 또는 산출물 ID>

## 비기능요구사항
### <REQ-NF-NNN> <제목>
- 서술: ...
- ISO25010 특성: ...
- 검증 방안: 도구/절차/임계값/판정기준
- 추적 링크: ...

## 일관성/추적성 점검 결과
- 모순 발견 여부: ...
- traceability-matrix.md 갱신 여부: ...
```

산출물 작성이 끝나면 §2~§6 기준을 항목별로 스스로 재검토한 결과를 요약해 사용자에게 보고한다 (어떤 기준을 충족했고, 어떤 부분이 보완이 필요한지).
