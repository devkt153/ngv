# 상세설계 스킬

이 스킬은 소프트웨어 상세설계 산출물을 작성하거나 검토할 때, 아래 모든 기준을 동시에 만족하도록 안내한다. 어느 하나라도 빠지면 산출물을 완료된 것으로 보고하지 않는다.

## 0. 템플릿 확인 (최우선, 매번 반복)

- 상세설계 관련 산출물은 저장소의 지정 템플릿을 **반드시** 사용한다. 스스로 구조를 지어내지 않는다.
  - SW 상세설계서 → `templates/WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-001_SW 상세설계서 템플릿.docx`
  - 상세설계 UML 및 호출관계 다이어그램 → `templates/WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-002_상세설계 UML 및 호출관계 템플릿.drawio`
  - Python 의존성 SBOM/FOSS 라이선스 목록(외부 라이브러리 사용 시) → `templates/WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SBOM-001_Python 의존성 SBOM FOSS 라이선스 목록 템플릿.xlsx`
  - 양방향 요구사항 추적 매트릭스(아키텍처 요소→상세설계 유닛 할당) → `templates/WP_Templates/Engineering/Traceability/TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx`
  - 템플릿 ID·적용 산출물·실사용 파일 위치 등록부 → `templates/WP_Templates/PRC-TPL-001_표준 산출물 양식 등록부.xlsx` (신규 산출물 작성 시 이 등록부에도 파일 위치를 기록한다)
  - 후속 산출물과의 정합성 확인용(직접 작성 대상 아님) → 단위시험 템플릿 `templates/WP_Templates/Engineering/SoftwareUnitVerification/TPL-SWE4-001_SW 단위시험 명세서 템플릿.xlsx` (§6의 유닛 시험 관점이 이 문서의 입력이 됨)
- 상위 입력 산출물(직접 수정 대상 아님, 정합성만 확인) → 아키텍처 설계서 `TPL-SWE2-001`, 아키텍처 UML `TPL-SWE2-002` (architecture-designer 스킬 산출물)
- 템플릿 사용 규칙 (`templates/WP_Templates/Engineering/README.md` 기준):
  - DOCX: 각 제목 아래 작성 안내를 실제 프로젝트 내용으로 교체한다. 장/절 구조 자체는 임의로 바꾸지 않는다.
  - XLSX: 기존 시트/열 구조를 유지하고, 안내가 있는 행 다음 실제 데이터부터 채운다.
  - DRAWIO: 안내 도형을 지우고 실제 유닛·호출관계·추적 ID로 채운다. 검토본/베이스라인 생성 시 PNG를 함께 내보낸다.
  - 산출물 파일명은 템플릿을 복사한 뒤 `<산출물 ID>_<산출물명>.<확장자>` 형식으로 바꾼다.
- 위 템플릿이 다루지 않는 보조 산출물만 예외적으로 마크다운 골격(§9 출력 형식)을 임시로 사용하고, 그 사실을 산출물에 명시한다.

## 1. 표준 준수 범위

- **A-SPICE SWE.3 (Software Detailed Design and Unit Construction)**: 상세설계 산출물이 다음을 충족하는지 자체 점검한다 — 아키텍처 요소가 구현 가능한 수준의 유닛(모듈/클래스/함수)으로 구체화됨, 유닛 인터페이스가 아키텍처 인터페이스와 정합되어 정의됨, 유닛의 동적 동작이 기술됨, (해당 시) 자원 사용 목표가 정의됨, 아키텍처↔상세설계↔요구사항 양방향 추적성이 확보됨, 일관성이 유지됨. 정확한 기본관행(BP) 문구는 조직이 보유한 공식 A-SPICE 4.1 PAM으로 대조 확인이 필요하다.
- **ISO 26262 Part 6, Clause 8 (Software unit design and implementation)**: 유닛설계는 구현자가 추가 정보 없이 바로 코드로 옮길 수 있는 수준의 상세도(알고리즘, 자료구조, 제어흐름)로 명시해야 한다. ASIL 등급에 따른 설계·구현 원칙(§5)을 따르고, 코딩 가이드라인 준수 및 정적분석 계획을 포함한다. 표기법(자연어/의사코드·흐름도/UML/정형)과 검증 방법(워크스루, 페어프로그래밍, 의미분석, 제어/데이터 흐름 분석, 정적 코드분석, 코딩 가이드라인 준수 점검 등)은 ASIL 등급에 맞게 선택한다. 정확한 표·조항 번호는 조직이 보유한 공식 ISO 26262:2018 Part 6 문서로 대조 확인이 필요하다.

## 2. 선행 확인 — 아키텍처 근거 확보 (필수)

- 상세설계 대상 유닛은 반드시 확정된 아키텍처 설계서(`TPL-SWE2-001`)의 컴포넌트에 매핑되어야 한다. 아키텍처에 없는 유닛을 임의로 새로 만들지 않는다.
- 아키텍처 산출물이 없거나 불명확하면, 상세설계를 진행하지 말고 architecture-designer 스킬 산출물을 먼저 확보하거나 사용자에게 확인한다.
- 아키텍처에서 정의된 컴포넌트 인터페이스(제공/사용, 시그니처)는 상세설계에서 임의로 바꾸지 않는다. 시그니처 변경이 꼭 필요하면 "아키텍처 변경 필요" 사항으로 별도 보고하고, 확정 전까지 상세설계를 완료 처리하지 않는다.

## 3. 응집력·결합도·SOLID — 유닛 수준 재확인 (필수, 완화 불가)

- 각 유닛(모듈/클래스/함수)은 단일하고 명확한 책임만 가져야 한다(높은 응집력). 서로 관련 없는 로직이 한 유닛에 섞여 있으면 분리한다.
- 유닛 간 통신은 §4에서 정의한 인터페이스를 통해서만 이루어진다. 다른 유닛의 내부 상태에 직접 접근, 전역 가변 상태 공유, 구체 클래스에 대한 직접 의존(추상화 없이), 순환 의존은 결합도 위반으로 간주하고 재설계한다.
- SOLID 5원칙(SRP/OCP/LSP/ISP/DIP)을 유닛/클래스 설계에도 동일하게 적용한다. 위반이 있으면 재설계하거나 근거를 명시적으로 기록한다.
- 알고리즘/자료구조 선택지가 여러 개이고 성능·복잡도·안전성 트레이드오프가 유의미한 경우(특히 안전 관련 유닛), 대안을 간단히 비교한 뒤 선택 근거를 기록한다. 사소한 유닛까지 매번 대안 비교를 강제하지는 않는다.
- **표 작성 원칙(완화 불가)**: 템플릿에 표 형식이 지정되어 있지 않아도, 나열형·비교형·대응관계형 내용(코딩 원칙 점검 결과, 자원 목표, 매핑 관계 등 병렬적인 항목들)은 줄글로 풀어 쓰지 않고 적절한 열을 갖춘 표로 작성한다. 서술이 자연스러운 목적·배경 설명만 줄글로 남긴다.

## 4. 유닛 인터페이스·알고리즘·자료구조 정의 (필수)

각 유닛마다 다음 항목을 모두 명시해야 "정의됨"으로 인정한다:

- 유닛 ID, 소속 아키텍처 컴포넌트, 책임(단일 책임 여부)
- 인터페이스: 오퍼레이션 시그니처(입출력 파라미터 타입/단위/유효범위, 반환값), 사전조건/사후조건, 오류·예외 처리 방식 — 아키텍처 인터페이스와 일치해야 함
- 알고리즘: 의사코드(pseudocode) 또는 흐름도(flowchart)로, 구현자가 추가 설계 판단 없이 코드로 옮길 수 있는 수준까지 상세화
- 자료구조: 필드, 타입, 불변식(invariant), 초기화 조건
- 호출 관계: 이 유닛이 호출하는 유닛과 이 유닛을 호출하는 유닛(양방향)
- 자원 사용 목표(해당 시): 실행 시간, 메모리 사용량, 스택 깊이 등
- **다음과 같은 표현은 상세설계로 인정하지 않는다**: "적절히 처리한다", "필요시 예외처리", "TODO", 알고리즘 단계가 실제 구현 결정을 요구자에게 다시 떠넘기는 서술. 발견 시 완료 처리하지 말고 구체화하거나 사용자에게 필요한 정보를 확인한다.

## 5. 코딩·구현 원칙 (ISO 26262-6 Clause 8, 필수)

- 유닛이 상속하는 ASIL 등급에 따라 아래 설계/구현 원칙 준수 여부를 점검하고 산출물에 기록한다:
  - 단일 진입점/단일 종료점, 무조건 점프(goto) 금지 또는 제한
  - 순환복잡도(cyclomatic complexity)를 프로젝트 임계값 이내로 유지, 함수 크기 제한
  - 재귀 사용 제한(특히 ASIL C/D는 금지 권장), 동적 메모리 할당 제한(ASIL C/D는 금지 권장)
  - 포인터 사용 제한, 인터럽트 사용 제한, 전역 변수 최소화
  - 데드코드 금지, 암묵적(숨은) 데이터/제어흐름 금지, 명시적 타입 변환만 허용
- 프로젝트가 따를 코딩 가이드라인(예: MISRA C/C++, 언어별 스타일 가이드)과 정적분석 도구·규칙셋 계획을 명시한다. 가이드라인이 지정되어 있지 않으면 사용자에게 확인한다(임의로 특정 가이드라인을 확정하지 않는다).
- 외부 라이브러리/오픈소스 의존성을 도입하는 경우 `TPL-SBOM-001`에 등록하고 라이선스 호환성(카피레프트 여부 등)을 확인한다.

## 6. 동적 동작 및 단위시험 연계

- 유닛 간 호출 순서·주요 시나리오를 Sequence/Activity Diagram으로 표현한다.
- 경계값, 예외 경로, 오류 처리 경로 등 유닛 수준 시험 관점을 식별해 명시한다. 이 항목은 `TPL-SWE4-001`(SW 단위시험 명세서) 작성의 입력이 됨을 산출물에 명시하고, 두 문서 간 불일치가 없는지 확인한다.

## 7. 다이어그램

- `TPL-SWE3-002` drawio 템플릿을 사용한다.
- **다이어그램 렌더링 원칙(완화 불가)**: 상세설계서(docx) 본문에 Mermaid/PlantUML 원본 소스를 텍스트(코드블록)로 그대로 넣지 않는다. 원본은 `deliverables/diagrams/<산출물ID>-<식별자>.mmd`(또는 `.puml`)로 별도 저장하고, 이미지(PNG 등)로 렌더링한 결과를 문서에 삽입한다. 렌더링 도구가 전혀 없으면 matplotlib 등 가용한 도구로 동등한 내용을 직접 그려 이미지로 저장한다. 사용자와 초안을 검토하는 대화 중간 단계에서만 코드블록을 임시로 써도 된다.
- 최소한 다음을 포함한다: Class/Module Diagram(유닛 구조 및 호출관계), 유닛별 알고리즘 흐름도 또는 의사코드, 주요 시나리오 Sequence Diagram, 상태를 가진 유닛은 State Machine Diagram.
- 각 다이어그램에는 관련 유닛 ID·인터페이스 ID를 라벨/주석으로 명시해 추적이 끊기지 않게 한다.

## 8. 추적성

- 각 유닛은 하나 이상의 아키텍처 컴포넌트에, 각 아키텍처 컴포넌트는 하나 이상의 유닛에 매핑되어야 한다. `TPL-TRC-001` 매트릭스를 갱신해 요구사항→아키텍처 요소→상세설계 유닛의 사슬을 유지한다.
- 아키텍처 요소 중 상세설계 유닛이 없는 것("미구체화")이나, 어떤 아키텍처 요소에도 속하지 않는 유닛("고아 유닛")은 완료로 보지 않고 사용자에게 보고한다.

## 9. 일관성 및 검증

- 아키텍처 인터페이스 시그니처와 상세설계 유닛 인터페이스가 정확히 일치하는지 확인한다.
- §5 코딩·구현 원칙 위반 여부, 표기법(다이어그램 종류·의사코드 스타일) 일관성을 점검한다.
- ISO 26262-6에서 언급하는 검증 방법(워크스루, 페어프로그래밍, 의미분석, 제어/데이터 흐름 분석, 정적 코드분석, 코딩 가이드라인 준수 점검) 중 어떤 방법으로 이 상세설계를 검토했는지 기록한다.

## 출력 형식

실제 산출물은 `TPL-SWE3-001` 템플릿의 장/절 구조를 그대로 채워 작성한다. 템플릿이 다루지 않는 보조 내용이나 초안 검토 단계에서만 아래 골격을 임시로 사용한다.

```

- 알고리즘(의사코드 또는 흐름도): ...
- 자료구조: ...

- 자원 사용 목표(해당 시): ...

## 코딩·구현 원칙 점검
