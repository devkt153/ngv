# SW 시스템 테스트 케이스 생성

## 0. 역할 범위 및 템플릿 (다른 파이프라인 스킬과의 경계)

- **이 스킬이 다루는 범위는 A-SPICE SWE.6(Software Qualification Test) 수준의 요구사항 기반 블랙박스 시스템 테스트뿐이다.** 아래는 이 스킬이 다루지 않으며, 각각 별도 스킬의 소관이다 — 서로 대체하거나 내용을 중복 정의하지 않는다:
  - 단위 수준 테스트(화이트박스, TDD Red-Green-Refactor, SWE.3/4 성격) → `coding`/`tdd` 스킬
  - 통합 순서·인터페이스 기반 통합시험, 함수/Call 구조적 커버리지 100% → `integration-tester` 스킬(SWE.5)
- **입력(테스트 베이시스, 직접 수정 대상 아님)**: SW 요구사항 명세서 `templates/WP_Templates/Engineering/SoftwareRequirementsAnalysis/TPL-SWE1-001_SW 요구사항 명세서 템플릿.docx`, Use Case 명세서 `TPL-SWE1-002_Use Case 명세서 템플릿.docx` (requirements-analyst 스킬 산출물). 요구사항 산출물이 없거나 불명확하면 테스트 케이스 설계를 시작하지 말고 requirements-analyst 산출물을 먼저 확보하거나 사용자에게 확인한다.
- **출력 템플릿(반드시 사용, 스스로 구조를 지어내지 않는다)**: SW 검증 명세서 `templates/WP_Templates/Engineering/SoftwareVerification/TPL-SWE6-001_SW 검증 명세서 템플릿.xlsx`, SW 검증 결과서 `templates/WP_Templates/Engineering/SoftwareVerification/TPL-SWE6-002_SW 검증 결과서 템플릿.xlsx`. §"산출물 구조"에 쓰인 시트/열 구성은 이 템플릿의 실제 시트 구조를 따른 것이며, 템플릿과 어긋나면 템플릿을 기준으로 삼는다.
- **추적성**: 양방향 요구사항 추적 매트릭스 `templates/WP_Templates/Engineering/Traceability/TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx`를 갱신해 요구사항 ↔ 시스템 테스트 케이스 매핑을 유지한다. 테스트 케이스가 없는 요구사항("미검증 요구사항")이나, 대응 요구사항이 없는 테스트 케이스("고아 케이스", "(제안)" 표시된 것은 예외)는 완료로 보지 않고 보고한다.
- **커버리지 개념 구분(다른 스킬과 혼동 금지)**: 이 스킬이 다루는 커버리지는 **요구사항 커버리지**(모든 기능/비기능 요구사항에 최소 1개 이상의 테스트 케이스가 대응하는지)이다. `integration-tester`의 **구조적 코드 커버리지**(함수 커버리지·Call 커버리지 100%)와는 별개의 지표이며, 이 스킬의 산출물에서 두 개념을 혼용하지 않는다.

## 기반지식

- **ISO 26262 Part 6, Clause 11 (Verification of software safety requirements)**: 통합된 임베디드 소프트웨어를 대상으로 소프트웨어 안전요구사항을 검증하는 요건. 특히 ASIL 등급이 할당된 요구사항은 판정기준의 전 분기(경계값, 조건 조합)를 빠짐없이 검증해야 한다. 정확한 조항 번호는 조직이 보유한 공식 ISO 26262:2018 Part 6 문서로 대조 확인이 필요하다.
- **A-SPICE SWE.6 (Software Qualification Test)**: 통합된 소프트웨어가 SW 요구사항(SWE.1 산출물)을 만족하는지 검증하는 Base Practice. 양방향 추적성(요구사항 ↔ 테스트 케이스)과 표준화된 시험 절차를 요구한다. 정확한 기본관행(BP) 문구는 조직이 보유한 공식 A-SPICE 4.1 PAM으로 대조 확인이 필요하다.
- **ISO 29119 및 ISTQB**: 테스트 시나리오·테스트 케이스 설계 프로세스와 용어 체계(긍정/부정 분류 등)의 근거로 사용합니다.
- **ISO 25000 (SQuaRE)**: 비기능(품질) 요구사항을 분류하는 기준입니다. 비기능 테스트 케이스는 이 표준의 품질 특성(예: 기능적합성, 성능효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성)별로 그룹화합니다.

## 적용 대상 테스트 기법

요구사항의 성격에 맞춰 아래 기법 중에서 선택하여 적용하고, 각 테스트 케이스의 "사용 기법" 항목에 실제로 적용한 기법을 명시합니다.

- **경계값 분석**: 검증기준에 수치·범위·임계값이 있는 경우, 경계값 미만/경계값/경계값 초과를 각각 별도 케이스로 도출합니다.
- **동치 클래스(동등분할)**: 입력 도메인을 유효/무효 클래스로 나누어 대표값을 도출합니다.
- **조합 테스트(전 조건 조합)**: 관련 조건 수가 적어 전수 조합이 실행 가능한 범위일 때 우선 적용합니다.
- **페어와이즈**: 조건·값의 조합 수가 많아 전수 조합 테스트가 비현실적인 경우에 대체 적용합니다.
- **엣지 케이스**: 정상 범위의 극단, 동시성/타이밍 등 일반 분석 기법으로 포착되지 않는 특이 조건을 다룹니다.
- **경험 기반 테스트**: 유사 시스템의 결함 이력이나 QA 경험에 근거해 오류를 추정합니다(오류 추정, 탐색적 테스트 등).

## 작성 원칙

- 의미 없이 테스트 케이스 개수만 늘리지 않습니다.
- 테스트의 예상 결과를 임의로 가정하지 않습니다. 명세서에 근거가 없다면 이 스킬을 사용하는 에이전트가 사용자에게 확인을 받아야 합니다.
- 이 스킬의 커버리지 목표는 **요구사항 커버리지 100%**(모든 기능/비기능 요구사항에 최소 1개 이상의 테스트 케이스 대응)이다. 코드 수준의 함수/Call 커버리지(정의: `integration-tester` 스킬 §5)와 혼동하지 않는다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성합니다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, 이 스킬을 사용하는 에이전트를 통해 사용자 검토를 받습니다.
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하고 싶은 테스트 케이스는 테스트 케이스명 끝에 "(제안)"이라고 표시해 구분합니다.
- 사용한 테스트 설계 기법을 각 케이스에 명시합니다.

## 도구 사용

- 페어와이즈 조합을 생성할 때는 오픈소스인 PICT를 사용합니다.
- 전수 조합(모든 조건의 조합)을 생성할 때는 PICT의 `/o:max` 옵션을 사용합니다.

## 산출물 구조

`TPL-SWE6-001`(SW 검증 명세서 템플릿)의 실제 시트 구조를 따른다. 아래는 그 구조에 맞춰 채워야 할 개념적 구성이며, 실제 시트/열 이름이 다르면 템플릿을 기준으로 삼는다:

- 기능 요구사항에 대한 테스트 케이스: "테스트 케이스" 시트
- 비기능 요구사항에 대한 테스트 케이스: 별도의 "비기능 테스트 케이스" 시트, ISO 25000 품질 특성별로 구분
- 요구사항 원문에 없거나 원문보다 엄격하게 사용자 확인을 거쳐 확정한 판정기준: "확정 근거" 열에 확정 일자와 승인 주체 기록
- 시험 수행 결과는 `TPL-SWE6-002`(SW 검증 결과서 템플릿)에 기록한다.
- 완료 전 `TPL-TRC-001` 추적 매트릭스를 갱신하고, 미검증 요구사항·고아 케이스 여부를 점검해 보고한다.

## 완료 판정 — 테스트 성공률 100% (필수, 완화 불가)

- 실행된 시스템 테스트 케이스는 fail 없이 모두 pass해야 한다("(제안)" 케이스 중 사용자가 채택하지 않은 것은 제외). 테스트 성공률 100%를 달성하지 못하면 완료로 보고하지 않는다.
- fail한 케이스는 요구사항 미충족(결함)으로 `TPL-SWE6-002`에 기록하고, 결함 수정 후 재시험해 다시 pass를 확인한다. fail을 "알려진 이슈"로 남겨둔 채 완료 처리하지 않는다.
- 이 성공률 지표는 §"역할 범위 및 템플릿"에서 정의한 **요구사항 커버리지**(모든 요구사항에 케이스가 있는지)와는 별개다 — 커버리지는 "케이스가 존재하는가", 성공률은 "그 케이스가 통과했는가"를 뜻하며 둘 다 100%여야 완료로 본다.
