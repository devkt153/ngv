# TDD 스킬 (Red-Green-Refactor)

> 이 스킬은 [obra/superpowers](https://github.com/obra/superpowers)의 `test-driven-development` 스킬(및 `writing-good-tests.md`)을 이 프로젝트(Python 3.14 + unittest, `coding` 스킬 연계)에 맞게 각색한 것이다. 기존 프로젝트 tdd 스킬에서 쓰던 "착수 전 설계 계약 확인"(§0)과 "사이클 보고 형식"(§6)은 그대로 유지한다.

## 개요

테스트를 먼저 쓴다. 실패를 직접 확인한다. 통과시키는 최소한의 코드를 쓴다.

**핵심 원칙:** 테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 맞는 것을 검증하는지 알 수 없다.

**규칙의 문구를 어기는 것은 규칙의 정신을 어기는 것이다.**

## 0. 착수 전 확인 (프로젝트 규칙)

- 구현하려는 유닛의 계약(인터페이스 시그니처, 사전/사후조건, 오류 처리, 자료구조)을 상세설계 산출물(`TPL-SWE3-001` 등, detailed-designer 스킬 산출물)에서 확인한다. 계약이 없거나 불명확하면 임의로 지어내지 말고 사용자에게 확인한다.
- 해당 유닛에 대해 이미 식별된 단위시험 관점(경계값, 예외 경로 — 상세설계 §6 또는 `TPL-SWE4-001`)이 있으면 테스트 케이스 목록의 기반으로 사용한다.
- 테스트 프레임워크는 프로젝트 지침에 따라 `unittest`만 사용한다(다른 프레임워크를 임의로 도입하지 않는다).

## 언제 적용하는가

**항상:** 신규 기능, 버그 수정, 리팩토링, 동작 변경.

**예외(사용자에게 확인 후에만):** 일회성 프로토타입, 자동 생성 코드, 설정 파일.

"이번만 TDD를 생략하자"는 생각이 든다면 멈춘다. 그것은 합리화다.

## 철칙 (Iron Law)

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다
```

테스트보다 코드를 먼저 썼다면? 삭제하고 처음부터 다시 시작한다.

**예외 없음:**
- "참고용"으로 남겨두지 않는다
- 테스트를 쓰면서 그 코드를 "적당히 재활용"하지 않는다
- 쳐다보지 않는다
- 삭제는 삭제다

테스트로부터 새로 구현한다. 예외 없음.

## Red-Green-Refactor

### RED — 실패하는 테스트 작성

검증하려는 동작 하나를 보여주는 최소한의 테스트를 작성한다.

<Good>
```python
def testRetryOperationSucceedsOnThirdAttempt(self):
    """!
    \\brief 두 번 실패한 뒤 세 번째 시도에서 성공하면 결과를 반환하는지 검증한다.
    \\technique 경계값분석 (허용 재시도 횟수의 마지막 경계)
    \\case 긍정(Positive)
    """
    attempts = {"count": 0}

    def operation():
        attempts["count"] += 1
        if attempts["count"] < 3:
            raise RuntimeError("fail")
        return "success"

    result = retryOperation(operation)

    self.assertEqual(result, "success")
    self.assertEqual(attempts["count"], 3)
```
명확한 이름, 실제 코드 대상, 한 가지 동작만 검증
</Good>

<Bad>
```python
def test_retry(self):
    mockOp = MagicMock(side_effect=[RuntimeError(), RuntimeError(), "success"])
    retryOperation(mockOp)
    self.assertEqual(mockOp.call_count, 3)
```
모호한 이름(3글자 미만 축약 없음이지만 의도 불명), 실제 코드가 아니라 mock 자체를 검증, 문서화 태그 없음
</Bad>

**요구사항:**
- 한 가지 동작만
- 명확한 이름(3글자 이상, 낙타표기법 — `coding` 스킬 네이밍 규칙과 동일하게 테스트 코드에도 적용)
- 실제 코드 대상(불가피한 경우가 아니면 mock 금지 — 자세한 기준은 `writing-good-tests.md` 참조)
- §5에서 정한 Doxygen 스타일 문서화(목적/기법/케이스 종류)를 반드시 포함

### Verify RED — 실패를 직접 확인 (필수, 생략 불가)

```bash
python -m unittest <module>.<TestClass>.<test_method> -v
```

확인할 것:
- 테스트가 "에러(error)"가 아니라 "실패(failure)"로 끝나는가
- 실패 메시지가 예상과 일치하는가
- 오타가 아니라 기능이 아직 없어서 실패하는가

**테스트가 통과해버리면?** 이미 존재하는 동작을 테스트하는 것이다 — 테스트를 다시 작성한다.

**테스트가 에러로 끝나면?** 에러를 고치고, "의도한 이유로 실패"할 때까지 재실행한다.

### GREEN — 최소 구현

테스트를 통과시키는 가장 단순한 코드만 작성한다.

<Good>
```python
def retryOperation(operationFn, maxAttempts=3):
    lastError = None
    for attemptIndex in range(maxAttempts):
        try:
            return operationFn()
        except Exception as caughtError:
            lastError = caughtError
    raise lastError
```
테스트를 통과시키는 데 딱 필요한 만큼만
</Good>

<Bad>
```python
def retryOperation(operationFn, maxAttempts=3, backoffStrategy="linear",
                    onRetryCallback=None, jitter=False):
    # YAGNI: 아직 어떤 테스트도 요구하지 않은 옵션들
    ...
```
과잉설계(아직 필요하지 않은 기능을 미리 추가)
</Bad>

기능 추가, 다른 코드 리팩토링, 요청받지 않은 "개선"을 하지 않는다.

### Verify GREEN — 통과를 직접 확인 (필수, 생략 불가)

```bash
python -m unittest discover
```

확인할 것:
- 대상 테스트가 통과하는가
- 기존 테스트가 모두 계속 통과하는가
- 출력이 깨끗한가(에러/경고 없음)

**테스트가 실패하면?** 테스트가 아니라 코드를 고친다.

**다른 테스트가 깨지면?** 지금 바로 고친다.

### REFACTOR — 정리

그린 상태에서만 진행한다:
- 중복 제거
- 이름 개선
- 헬퍼 추출

테스트는 계속 그린으로 유지한다. 새 동작을 추가하지 않는다.

이 프로젝트에서는 이 단계에서 `coding` 스킬이 요구하는 품질지표(함수 라인수 ≤50, 순환복잡도 ≤10, 중복 코드 7라인 이하, Doxygen 주석 비율 20% 이상, 네이밍 3자 이상 camelCase)를 재확인한다. 기준을 넘는 항목이 있으면 이 단계에서 해소하고, 해소되기 전까지 사이클을 완료로 보지 않는다.

### 반복

다음 요구 동작이나 경계조건에 대해 RED부터 다시 시작한다. 상세설계에서 식별된 모든 단위시험 관점(경계값/예외 경로 포함)을 커버할 때까지 사이클을 반복한다.

## 좋은 테스트

| 품질 | 좋은 예 | 나쁜 예 |
|---|---|---|
| **최소성** | 한 가지만 검증. 이름에 "그리고/and"가 들어가면 나눈다 | `test이메일과도메인과공백을검증한다` |
| **명확성** | 이름이 동작을 설명한다 | `test1`, `testCase가` |
| **의도 표현** | 원하는 API를 보여준다 | 코드가 무엇을 해야 하는지 감춘다 |

테스트를 작성하거나 수정할 때, 또는 mock/헬퍼를 추가할 때는 `writing-good-tests.md`를 읽는다. 핵심 규칙:
- 테스트를 실패하게 만들 프로덕션 변경을 먼저 이름 붙인다
- 실제 동작에만 단언(assert)하고, mock의 동작에는 단언하지 않는다
- 테스트 전용 코드는 테스트 유틸리티에 두고 프로덕션 클래스에 넣지 않는다
- 무언가를 mock하기 전에 그 의존성의 부수효과를 먼저 이해한다

## 흔한 합리화와 반박

| 핑계 | 실제로는 |
|---|---|
| "너무 단순해서 테스트할 필요 없다" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "나중에 테스트할게" | 나중에 쓴 테스트는 바로 통과한다 — 아무것도 증명하지 못한다. |
| "결과는 나중에 테스트해도 똑같다" | 사후 테스트는 "이 코드가 뭘 하는가"에 답하고, 사전 테스트는 "이 코드가 뭘 해야 하는가"에 답한다. |
| "이미 수동으로 테스트했다" | 수동 테스트는 즉흥적이며 커버리지 기록이 남지 않는다. |
| "지금까지 쓴 시간이 아깝다" | 매몰비용 오류다. 신뢰할 수 없는 코드를 유지하는 것이 진짜 낭비다. |
| "일단 참고용으로 남기고 테스트를 쓸게" | 결국 그 코드를 손보게 된다. 그것도 사후 테스트다. 삭제는 삭제다. |
| "TDD는 나를 느리게 만든다" | TDD는 커밋 전에 버그를 잡고 회귀를 막는다. "실용적" 지름길은 결국 프로덕션 디버깅으로 이어진다. |

## 위험 신호 — 발견하면 코드를 지우고 다시 시작

- 테스트보다 코드가 먼저 있다
- 구현 후에 테스트를 붙였다
- 테스트가 바로 통과해버렸다
- 왜 실패했는지 설명할 수 없다
- 테스트를 "나중에" 추가했다
- "이번만은" 예외라고 합리화하고 있다
- "이 경우는 다르다"는 식의 변명

## 완료 전 체크리스트

- [ ] 새로 추가된 함수/메서드마다 테스트가 있다
- [ ] 구현하기 전에 각 테스트가 실패하는 것을 직접 확인했다
- [ ] 각 테스트가 예상한 이유로 실패했다(오타가 아니라 기능 부재)
- [ ] 각 테스트를 통과시키는 최소한의 코드를 작성했다
- [ ] 모든 테스트가 통과한다
- [ ] 출력이 깨끗하다(에러/경고 없음)
- [ ] 테스트가 실제 코드를 대상으로 한다(mock은 불가피한 경우만)
- [ ] 경계조건과 오류 경로가 커버되었다
- [ ] **(이 프로젝트 전용)** 모든 테스트 함수에 §5의 Doxygen 목적/기법/케이스 태그가 있다
- [ ] **(이 프로젝트 전용)** 식별된 경계값/예외 경로마다 부정(Negative) 케이스가 최소 하나 존재한다

모든 항목을 체크할 수 없다면 TDD를 건너뛴 것이다. 처음부터 다시 시작한다.

## 막혔을 때

| 문제 | 해결 |
|---|---|
| 어떻게 테스트할지 모르겠다 | 원하는 API를 먼저 적어본다. 단언(assert)부터 쓴다. 사용자에게 묻는다. |
| 테스트가 너무 복잡하다 | 설계가 복잡한 것이다. 인터페이스를 단순화한다. |
| 전부 mock해야 한다 | 코드가 너무 결합되어 있다. 의존성 주입을 사용한다. |
| 테스트 준비(setup)가 방대하다 | 헬퍼로 추출한다. 그래도 복잡하면 설계를 단순화한다. |

## 디버깅 연계

버그를 발견했는가? 그 버그를 재현하는 실패 테스트부터 작성한다. 그 다음 TDD 사이클을 따른다. 테스트가 수정을 증명하고 회귀를 막는다.

테스트 없이 버그를 고치지 않는다.

## 5. 테스트 문서화 규칙 — 기법·긍정/부정·Doxygen 목적 (이 프로젝트 전용, 완화 불가)

모든 테스트 함수(메서드)의 docstring에는 Doxygen 스타일 태그로 다음 세 가지를 **반드시** 포함한다:

- `\brief` — 이 테스트가 검증하는 목적/시나리오를 한 문장으로 서술.
- `\technique` — 이 테스트를 설계할 때 사용한 테스트 기법. 아래 중 해당하는 것을 명시하고(복수 가능), 목록에 없는 기법을 썼다면 이름을 그대로 적는다:
  - 동등분할(Equivalence Partitioning)
  - 경계값분석(Boundary Value Analysis)
  - 오류추정(Error Guessing)
  - 상태전이(State Transition Testing)
  - 결정테이블(Decision Table Testing)
  - 페어와이즈/조합(Pairwise/Combinatorial Testing)
  - 예외경로(Exception Path Testing)
- `\case` — `긍정(Positive)`(유효한 입력/정상 흐름 검증) 또는 `부정(Negative)`(잘못된 입력/오류·예외 흐름 검증) 중 해당하는 것을 명시.

예시:

```python
class TestRetryOperation(unittest.TestCase):

    def testRetryOperationSucceedsOnThirdAttempt(self):
        """!
        \\brief 두 번 실패한 뒤 세 번째 시도에서 성공하면 결과를 반환하는지 검증한다.
        \\technique 경계값분석 (허용 재시도 횟수의 마지막 경계)
        \\case 긍정(Positive)
        """
        ...

    def testRetryOperationRaisesAfterMaxAttemptsExceeded(self):
        """!
        \\brief 허용된 재시도 횟수를 모두 소진하면 마지막 예외가 그대로 전파되는지 검증한다.
        \\technique 오류추정 + 경계값분석 (허용 횟수 초과 지점)
        \\case 부정(Negative)
        """
        ...
```

- 상세설계(§6, `TPL-SWE4-001`)에서 식별된 경계값·예외 경로 각각에 대해 최소 하나의 부정(Negative) 케이스 테스트가 존재해야 한다. 긍정 케이스만 있고 부정 케이스가 없는 유닛은 완료로 보지 않는다.
- 이 문서화 규칙은 `coding` 스킬의 완료 조건 체크리스트에서도 재확인 대상이다.

## 6. 보고 형식 (프로젝트 규칙)

각 사이클마다 다음을 간단히 기록한다(상위 `coding` 스킬의 산출물에 포함):

```
### 사이클: <검증한 동작/조건>
- Red: 추가한 테스트, \brief/\technique/\case 요약, 실패 확인 결과
- Green: 구현 요약
- Refactor: 개선 내용 및 품질지표 재확인 결과
```

## 최종 규칙

```
프로덕션 코드 → 테스트가 먼저 존재했고 실패했음이 확인됨
그렇지 않으면 → TDD가 아니다
```

사용자(human partner)의 허락 없이는 예외를 두지 않는다.
