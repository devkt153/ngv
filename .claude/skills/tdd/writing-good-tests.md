# 좋은 테스트 작성하기

**이 문서를 읽어야 할 때:** 테스트를 새로 쓰거나 수정할 때, mock을 추가할 때, 테스트용 cleanup/헬퍼 메서드를 추가할 때.

> [obra/superpowers](https://github.com/obra/superpowers)의 `test-driven-development/writing-good-tests.md`를 이 프로젝트(Python/unittest)에 맞게 각색한 것이다.

## 개요

테스트는 특정한 문제(break)를 잡아내기 위해 존재한다. 다음 두 원칙이 전부를 지배한다:

```
1. 모든 테스트는 자신이 잡아내는 문제를 이름으로 밝힌다
2. 모든 테스트는 실제 대상을 검증한다
```

엄격한 TDD는 이 둘을 자연스럽게 만족시킨다: 먼저 작성되어 실제 코드에 대해 실패하는 것을 확인한 테스트는 이미 "실패할 수 있음"을 증명한 것이고, 실제 의존성이 느리거나 외부적일 때만 mock을 쓸 자격을 얻는다.

## 원칙 1: 잡아낼 문제를 먼저 이름 붙인다

테스트 본문을 쓰기 전에 답한다: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그 변경은 버그인가, 설계 결정인가?** 테스트는 잘못된 분기, 누락된 부수효과, 잘못된 인자, 경계조건, 깨진 계약 중 하나를 잡아낼 때 존재 가치가 있다.

**기대값은 독립적으로 계산한다.** 리터럴 값이나 직접 검산한 픽스처를 사용한다 — 리터럴 `want` 값을 쓰는 테이블 기반 테스트가 선호된다. 테스트 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과한다:

```python
# ❌ 거울 단언: 같은 빌더로 양쪽을 계산 — 항상 참
expected = buildSearchQuery(tag="urgent")
self.assertEqual(buildSearchQuery(tag="urgent"), expected)

# ✅ 손으로 검산한 리터럴
self.assertEqual(buildSearchQuery(tag="urgent"), 'tag:"urgent"')
```

**변경 감지기(change detector)를 만들지 않는다.** 의도적인 결정(상수 값, 정확한 메시지 문구, 내부 구조)만 실패시킬 수 있는 테스트는 재설계 때마다 울리고 버그 앞에서는 잠든다. 결정 자체가 아니라 그 결정에 의존하는 동작을 테스트한다: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출은 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증한다.

**동작을 검증하지, 텍스트를 검증하지 않는다.** 스크립트·스킬·설정 파일이 특정 줄을 포함하는지 검사하는 것은 "원본이 원본"이라는 사실만 증명한다. 통제된 입력으로 스크립트를 실행하고 출력·부수효과·종료 코드를 단언한다.

**프레임워크가 아니라 우리 코드를 테스트한다.** 우리 코드가 경계에서 맺는 계약(등록하는 라우트, 발행하는 쿼리, 만들어내는 페이로드)을 테스트한다. 업스트림(표준 라이브러리, 서드파티 프레임워크)의 동작은 그것을 만든 쪽의 테스트 몫이다. 업스트림 동작이 예상과 달라 놀랐다면, 그 가정을 이름 붙인 좁은 특성화(characterization) 테스트 하나만 작성한다. 같은 경계가 우리 코드 내부에도 적용된다: 생성자, getter, 상수, 단순 위임은 값을 검증·정규화·기본값 설정·파생·강제하거나 부수효과를 일으킬 때만 테스트할 가치가 있다 — 그렇지 않으면 그것에 의존하는 첫 번째 관찰 가능한 결과를 단언한다.

### 게이트 함수

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패하게 만들 프로덕션 변경을 이름 붙인다.

  이름 붙일 수 없다              → 관찰 가능한 동작 중심으로 재설계
  "원본 텍스트가 바뀌었다"        → 실제로 실행해서 그 효과를 단언
  의도적 결정만 잡아낸다          → 변경 감지기다. 그 결정에 의존하는
                                   동작을 테스트한다

  기대값이 테스트 대상 코드 없이 도출되었는지 확인한다.
  IF 그 코드의 로직/헬퍼를 재사용한다면:
    리터럴이나 손으로 검산한 픽스처로 바꾼다
```

## 원칙 2: 실제 대상을 검증한다

**mock은 단언의 대상이 될 수 없다.** mock에 대한 단언은 mock이 있으면 통과하고 없으면 실패할 뿐, 그 컴포넌트에 대해서는 아무것도 말해주지 않는다. 실제 컴포넌트의 동작을 단언한다. mock 자체를 확인하고 있다면 mock을 걷어내거나 그 단언을 삭제한다.

```python
# ✅ 실제 동작
self.assertIsNotNone(page.find_element_by_role("navigation"))

# ❌ mock 존재 여부
self.assertTrue(sidebarMockCalled)
```

**적절한 수준에서 mock한다.** 실제 메서드의 모든 부수효과를 먼저 파악한 뒤, 느리거나 외부적인 연산만 mock하고 테스트가 의존하는 나머지는 실제로 둔다. 확신이 없으면 실제 구현으로 먼저 테스트를 돌려 실제로 무엇이 필요한지 관찰한다.

```python
# ❌ mock이 중복 탐지 로직이 읽는 설정 쓰기까지 삼켜버림
patch("toolCatalog.discoverAndCacheTools", return_value=None)

# ✅ 느린 서버 기동만 mock하고, 설정 쓰기는 실제로 둔다
patch("mcpServerManager.startServer")
```

**대역(double)을 구체적으로 만든다.** 인자·호출 횟수·순서가 계약의 일부라면 그것을 단언한다 — 아무거나 받아주는 가짜는 아무것도 검증하지 못한다. 성공/오류/잘못된 형식 등 각 분기마다 별도의 픽스처나 스파이를 둔다.

**mock 응답은 실제 구조를 완전히 반영한다.** 테스트가 읽는 필드만이 아니라 실제로 존재하는 전체 구조를 mock한다. 부분적인 mock은 다운스트림 코드가 누락된 필드를 읽을 때 조용히 실패한다 — 테스트는 통과하는데 통합 환경에서는 깨진다.

**프로덕션 클래스에는 프로덕션 메서드만 둔다.** 테스트에만 필요한 정리(cleanup)는 테스트 유틸리티에 두고, 프로덕션 클래스의 `destroy()` 같은 메서드로 만들지 않는다.

**mock이 비대해지면 실제 컴포넌트를 쓰는 통합 테스트로 전환한다.** mock 설정이 테스트 로직보다 커지거나, mock에 실제 컴포넌트의 메서드가 빠져 있거나, mock이 바뀔 때마다 테스트가 깨진다면 신호다.

### 게이트 함수

```
mock이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부수효과를 나열한다. 테스트가 의존하는 것은
  실제로 두고, 그보다 아래의 느리거나 외부적인 수준만 mock한다.

  mock 응답은 실제 구조를 완전히 반영한다.

  테스트만 호출하는 메서드는 테스트 유틸리티에 둔다.

  mock 자체를 단언하려는 중인가?
    mock을 걷어내거나 그 단언을 삭제한다.
```

## 테스트는 구현과 함께 완성된다

TDD 사이클 — 실패하는 테스트, 최소 구현, 리팩토링 — 이 곧 "완료"의 정의다. 그 동작이 필요로 하는 테스트만 딱 만든다: 사소한 코드와 사람이 읽는 산문에는 테스트가 필요 없고, 절차를 만족시키기 위해 쓴 테스트는 영원히 유지보수 비용만 남긴다.

## 뮤테이션 체크

작업을 끝내기 전에, 머릿속으로 프로덕션 코드를 하나씩 변형(mutate)해 본다. 아래와 같은 현실적인 변형마다 최소 하나의 테스트가 실패해야 한다:

- 잘못된 상수/인자
- 잘못된 분기 처리
- 누락된 상태 변경이나 부수효과
- 비어 있거나 기본값인 반환
- 0, 빈 값, None, 미인가, 잘못된 형식 입력에 대한 검증 누락

어떤 변형도 잡아내지 못한다면 그 동작은 보호되지 않고 있는 것이거나, 그 테스트가 동어반복(tautology)인 것이다.

## 빠른 참고표

| 이럴 때... | 이렇게 |
|---|---|
| 테스트를 하나 쓸 때 | 그것이 잡아낼 문제를 이름 붙인다 — 버그이지 설계 결정이 아니다 |
| 기대값을 만들 때 | 손으로 도출한다. 테스트 대상 코드로 계산하지 않는다 |
| 스크립트/문서를 테스트할 때 | 실행하거나 소비자를 통해 검증한다. 텍스트를 grep하지 않는다 |
| 의존성 테스트에 손이 갈 때 | 우리 코드와의 경계 계약을 테스트한다. 그들의 공식 동작이 아니다 |
| mock된 요소를 단언하고 싶을 때 | 실제 컴포넌트를 테스트하거나 mock을 걷어낸다 |
| 메서드를 mock하려 할 때 | 부수효과를 먼저 파악하고, 느리거나 외부적인 수준만 mock한다 |
| mock 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트 전용 정리(cleanup)가 필요할 때 | 테스트 유틸리티에 둔다 |
| mock 설정이 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 마칠 때 | 뮤테이션 체크를 실행한다 |

## 경고 신호

- 준비(setup)와 단언이 같은 객체를 공유해 항상 같음을 보장한다
- 패닉·크래시·selector 누락으로만 실패할 수 있다
- 의도적인 변경마다 실패하고 우발적인 손상에는 절대 실패하지 않는다
- 기대값이 반복문·빌더·헬퍼 뒤에 숨어 있다
- 소스 텍스트를 grep하거나, 제거된 심볼이 남아있는지 확인한다
- 프레임워크만 남아 있어도 여전히 통과할 테스트다
- 부수효과나 결과를 확인하지 않고 커버리지만을 위해 존재한다
- `*-mock`류 테스트 ID를 단언하거나, mock을 제거하면 실패한다
- 어떤 메서드가 테스트 파일에서만 호출된다
- mock 설정이 테스트의 절반 이상을 차지하거나, 왜 그 mock이 필요한지 설명할 수 없다
- "혹시 몰라서" mock한다
