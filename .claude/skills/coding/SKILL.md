# 구현(코딩) 스킬

이 스킬은 상세설계 산출물을 실제 코드로 구현할 때, 아래 모든 기준을 동시에 만족하도록 안내한다. 어느 하나라도 빠지면 산출물을 완료된 것으로 보고하지 않는다.

**역할 범위**: 이 스킬은 상세설계 유닛을 코드로 구현하고 `tdd` 스킬로 단위 수준 테스트를 만드는 것까지만 다룬다. 컴포넌트 간 통합 순서·구조적 커버리지(함수/Call) 검증은 `integration-tester` 스킬(SWE.5)의 소관이고, 요구사항 기반 블랙박스 시스템 테스트는 `sw-system-test` 스킬(SWE.6)의 소관이다 — 이 스킬에서 대신 수행하거나 내용을 중복 정의하지 않는다.

## 0. 선행 확인 — 설계 근거 확보 (필수)

- 구현 대상 유닛이 상세설계서(`templates/WP_Templates/Engineering/SoftwareDetailedDesignAndUnitConstruction/TPL-SWE3-001_SW 상세설계서 템플릿.docx`, detailed-designer 스킬 산출물)에 정의되어 있는지 먼저 확인한다. 없거나 대상 유닛이 불명확하면 구현을 시작하지 말고 detailed-designer 산출물을 먼저 확보하거나 사용자에게 확인한다.
- 상세설계에 정의된 인터페이스 시그니처, 알고리즘, 자료구조를 구현 계약으로 그대로 사용한다. 코딩 중 계약을 바꿔야 할 필요가 생기면 "상세설계 변경 필요" 사항으로 별도 보고하고, 임의로 확정하지 않는다.

## 1. 개발 환경 (CLAUDE.md 준수, 완화 불가)

- 언어: **Python 3.14**.
- 테스트 프레임워크: **unittest**만 사용한다(pytest 등 다른 프레임워크를 임의로 도입하지 않는다).
- 순환복잡도·함수 라인수 등 품질지표는 오픈소스 도구로 측정한다. 프로젝트에 아직 특정 도구가 지정되어 있지 않으면, 다음과 같은 대표적인 옵션을 사용자에게 제안하고 확인받는다(임의로 하나를 조용히 확정하지 않는다): 순환복잡도/라인수 — `radon`, `flake8`(+`mccabe`), `lizard`; 중복 코드 — `pylint`(중복 코드 검사); Branch 커버리지 — `coverage.py`(`--branch` 옵션); 코드 포맷/스타일 — 프로젝트가 별도로 지정하지 않는 한 강제하지 않는다.

## 2. TDD 방식 (필수, 반드시 `tdd` 스킬 사용)

- 구현은 **반드시** `tdd` 스킬을 (Skill 도구로) 호출하여 그 Red-Green-Refactor 절차를 그대로 따른다. 테스트 없이 구현 코드를 먼저 작성하지 않는다.
- 상세설계의 단위시험 관점(경계값/예외 경로)과, 존재한다면 `TPL-SWE4-001`(SW 단위시험 명세서)의 케이스를 테스트로 반영한다.
- `tdd` 스킬의 각 사이클 보고를 이 스킬의 최종 보고에 함께 포함한다.

## 3. 품질지표 (필수, CLAUDE.md 원문 기준 — 완화 불가)

- **함수 라인수**: 순수 코드 라인(공백 줄·주석 제외) 50라인 이하.
- **함수 순환복잡도**: 10 이하.
- **중복 코드**: 최대 7라인까지 허용한다(8라인 이상 동일/유사 코드 블록이 반복되면 함수·모듈로 추출한다).
- **주석**: Doxygen 방식(`\brief`, `\param`, `\return` 등 태그를 포함하는 docstring/주석)으로 작성하며, 파일(모듈) 단위로 주석 비율 20% 이상을 유지한다.
- **네이밍**: 함수명·변수명은 3글자 이상이어야 하며 **낙타표기법(camelCase)**을 사용한다. 이는 PEP8의 기본 관행(snake_case)보다 이 프로젝트 정책이 우선한다 — `i`, `j`, `x` 같은 2글자 이하 이름이나 snake_case 이름을 사용하지 않는다. 테스트 코드에도 동일하게 적용한다.
- 위 지표는 `tdd` 스킬의 Refactor 단계마다 재확인하고, §1에서 확인한 오픈소스 도구의 실행 결과(또는 재현 가능한 실행 명령)를 산출물에 기록한다. 기준을 넘는 항목이 있으면 완료로 보고하지 않는다.
- **Branch 커버리지 100%·테스트 성공률 100%**: 상세 기준과 예외 처리 절차는 `tdd` 스킬의 "커버리지 및 테스트 성공률" 절을 그대로 따른다(이 스킬에서 별도로 재정의하지 않는다).

## 4. 설계·코딩 원칙 연계

- 상세설계 단계에서 식별된 ASIL 기반 코딩 원칙(단일 진입/종료, 재귀·포인터·동적 메모리·인터럽트 사용 제한 등, 해당 시)과 프로젝트 코딩 가이드라인이 있으면 실제 코드에서도 동일하게 지킨다.
- 아키텍처/상세설계에서 정의한 인터페이스로만 컴포넌트·유닛 간 통신하는 코드를 작성한다. 다른 컴포넌트의 내부 상태에 직접 접근하거나 전역 가변 상태를 공유하는 방식으로 구현하지 않는다.
- 외부 라이브러리/오픈소스 의존성을 새로 도입하면 `TPL-SBOM-001`(Python 의존성 SBOM FOSS 라이선스 목록 템플릿)에 등록하고 라이선스 호환성을 확인한다.

## 5. 추적성

- 구현된 함수/모듈이 어떤 상세설계 유닛 ID를 구현한 것인지 주석(Doxygen 태그, 예: `\implements <유닛 ID>`) 또는 문서에 명시한다.
- `templates/WP_Templates/Engineering/Traceability/TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx`의 "하위 산출물(코드)" 항목을 실제 파일 경로·함수명으로 갱신한다.

## 6. 완료 조건 체크리스트

다음을 모두 만족해야 구현을 완료로 보고한다:

- [ ] 대상 유닛의 모든 요구 동작·경계조건에 대해 Red-Green-Refactor 사이클 완료
- [ ] `unittest` 전체 스위트 통과
- [ ] 함수 라인수 ≤ 50, 순환복잡도 ≤ 10 (오픈소스 도구 측정 결과로 확인)
- [ ] 중복 코드 8라인 이상 블록 없음
- [ ] Doxygen 주석 비율 20% 이상
- [ ] 함수명·변수명 3글자 이상 + camelCase
- [ ] 모든 테스트 함수에 `tdd` 스킬 §5 기준 Doxygen 태그(`\brief`/`\technique`/`\case`) 기재, 식별된 경계값·예외 경로마다 부정(Negative) 케이스 존재
- [ ] Branch 커버리지 100% (`coverage.py --branch` 등으로 실측)
- [ ] 테스트 성공률 100% (`unittest` 전체 스위트 실패/에러 0건)
- [ ] 컴포넌트 간 통신이 정의된 인터페이스로만 이루어짐
- [ ] `TPL-TRC-001` 추적 매트릭스 갱신
- 위 항목 중 하나라도 미충족이면 완료로 보고하지 않고, 어떤 항목이 왜 미흡한지 사용자에게 보고한다.
